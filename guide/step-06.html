Step 6 of 10

Build and deploy the app

When the infrastructure deployment succeeds, the App workflow starts on its own: it builds three images, pushes them to the private registry, waits for your approval, rolls them out to AKS and smoke-tests the public endpoint.

10 minGitHubAzure portalBrowserCI/CDSecurity

What you will do#

  • Watch the App (build & deploy to AKS) workflow build and push the images.
  • Approve the rollout to production.
  • Open Contoso Health and see the workloads in the Azure portal.

Build and push the images#

  1. In Actions, a run of App (build & deploy to AKS) started automatically after the infrastructure run.

  2. The Build & push images job needs no approval: it signs in with the main branch credential, logs in to the registry with Entra ID and pushes membership-api, bed-api and portal, each tagged with the commit SHA.

Approve the rollout#

  1. The Deploy to AKS job waits for production. Select Review deployments, tick production, Approve and deploy.

  2. The job gets cluster credentials with an Entra ID token (local accounts are disabled), renders the release with Kustomize, applies it, waits for each rollout and calls the public endpoint.

  3. The run summary shows the URL and version. The production environment link opens the app.

Open Contoso Health#

  1. Open http://contoso-health-<owner>.indonesiacentral.cloudapp.azure.com.

  2. Contribution status: members, paid, due by the 10th, not paid, collection rate, outstanding arrears; payment status by segment and class; a searchable member table.

  3. Bed availability: available beds per class across 22 hospitals, and per hospital.

See the workloads in the portal#

  1. Open the cluster aks-contoso-health, then Kubernetes resources, Workloads. Filter the namespace contoso-health: three Deployments, two replicas each.

  2. Services and ingresses: portal is the only LoadBalancer service; the APIs are internal (ClusterIP).

Check your work#

  • The App workflow run is green; its summary shows the URL and the image tag.
  • The app loads and the header shows the cluster, region and version.
  • In the portal, the three Deployments in contoso-health are all Ready.

How it works#

Immutable releases. Images are tagged with the commit SHA, never latest. The release manifest is rendered per run, so what runs in the cluster maps to exactly one commit, and a rollback is a revert of that commit.

No kubeconfig secrets. The cluster has local accounts disabled. The job asks Entra ID for a token for the AKS server application and uses it as the kubectl credential; Azure RBAC (AKS RBAC Cluster Admin, granted by Bicep) authorizes it.

Hardened workloads. Every pod runs as non-root with a read-only root file system, drops all Linux capabilities and uses the RuntimeDefault seccomp profile. HorizontalPodAutoscalers scale on CPU, PodDisruptionBudgets keep one replica during node drains, and NetworkPolicies deny all ingress except portal to APIs and the metrics agent.

Troubleshooting#

SymptomFix
Build job ends with Registry or cluster not readyThe infrastructure run has not finished or failed. Fix it, then re-run the App workflow.
Forbidden from kubectlThe identity lacks AKS RBAC Cluster Admin: check AZURE_PRINCIPAL_ID and re-run the infrastructure workflow.
Pods ErrImagePullThe kubelet identity lacks AcrPull on the registry, or the image tag does not exist. Check the role assignment created by Bicep.
Smoke test times outThe public IP is still provisioning. Re-run the failed job; the DNS name can take a minute to resolve.
