Create the deployment identity

GitHub Actions signs in to Azure as a user-assigned managed identity. No client secret exists anywhere: GitHub presents a short-lived OpenID Connect token, and Azure accepts it only from this repository, for the main branch, pull requests and the production environment.

How it works#

How the sign-in works

  1. A job that declares permissions: id-token: write asks GitHub's OIDC provider for a token. The token states who is asking: repository, branch, pull request or environment.
  2. azure/login sends the token to Microsoft Entra ID with the identity's client ID.
  3. Entra ID checks the issuer, the audience (api://AzureADTokenExchange) and the subject against the federated credentials. A different branch, a fork or another repository does not match.
  4. Entra ID returns an access token for the managed identity. It expires on its own; nothing is stored in GitHub.

The immutable subject format

The portal builds subjects as repo:OWNER@OWNER_ID/REPO@REPO_ID:…. Because the numeric IDs never change, a deleted and re-created repository with the same name cannot inherit the trust. We checked what GitHub actually sends: a token issued to this repository carries sub: repo:ibranibeny@66096127/contoso-health-aks-demo@1441838609:ref:refs/heads/…. Older repositories can still send the classic format (repo:OWNER/REPO:…); the subject must match character for character, so create the credentials in whichever format your token uses. azure/login prints the subject claim in the run log when a sign-in fails.

Why a condition on the RBAC role

The Bicep template creates role assignments, so the pipeline needs Microsoft.Authorization/roleAssignments/write. Owner or User Access Administrator would let a compromised workflow grant itself anything. The condition limits the identity to assigning two named roles, to users and service principals only, inside one resource group.
